# テスト設計: caucus/sprint-1（ST-2 MCP からの起票とスプリント計画 / ST-3 MCP からの承認・実行・レビュー）

## 組み合わせテスト

### 対象

今回追加した `PlanningTools`（`src/caucus_race/mcp/planning_tools.py`）の各ツールと、その下の
`PlanJobs` / `run_plan_job`（`src/caucus_race/plan_job.py`）。どれも引数と事前状態（DB 上の
スプリント・ストーリーの状態、計画ジョブのロックと状態ファイル）で振る舞いが変わる。
`server.py`（MCP の層）は、組み合わせとして分ける値を持たないため、この節では扱わない。MCP のクライアントから呼ぶテストは `tests/test_mcp_server.py` にある（下記「MCP の層と E2E」を参照）。

期待値の出典: タスクの受け入れ条件、README の MCP の節、docs/spec.md の R-3
（承認後は計画を変更できない）、既存の CLI と同じルール。例外の型とメッセージの詳細は
例外テストの観点で扱い、ここでは「例外（DomainError）になる」までと、拒否されたときに
状態が変わらないことを確認する。

### 共通の事前状態の同値クラス

| 因子 | クラス |
| --- | --- |
| スプリント S | none（一度も作っていない）/ planning / approved / active / review / closed（直前のスプリントが終了済みで、未終了のものはない） |
| ストーリーの状態 | backlog / planned（planning 内）/ planned（approved 内）/ queued（active 内）/ running / done（review 内）/ failed（review 内）/ suspended（review 内）/ done（closed 内）/ 存在しない ID |
| 計画ジョブ J | idle（実行したことがない）/ running（ロックを保持中）/ failed（前回失敗）/ succeeded（前回成功） |
| J を実行しているプロジェクト | 操作するプロジェクトと同じ / 別のプロジェクト |
| プロジェクト P | 存在する / 存在しない |

running のストーリーは、実行器（偽物）の中から操作して作る。failed と suspended は、実行器の結果を
error と blocked にして作る。終了時に failed・suspended はバックログに戻る（R-6）ため、
closed 内に残るのは done だけになる。

### 仕様不明（テストを書かない）

拒否するかどうかが仕様に書かれていないもの:

- 空文字: `add_story` の title、`create_sprint` の goal、`add_task` の title、`add_spike` の question
- `add_story` の受け入れ条件の要素が空文字のもの（例: `[""]`）
- プロジェクト名に `/` を含む場合。プロジェクト名の文字の制約が仕様になく、ロックと状態のファイルのパスが壊れる（別途報告済み）

### ST-3: 人間の判断にあたる操作（I〜R）

#### 対象

ST-3 で追加した `HumanTools`（`src/caucus_race/mcp/human_tools.py`）の各ツールと、
`BackgroundRunner.start_refine`（`src/caucus_race/runner.py`）、見直しの条件 `story_to_refine`
（`src/caucus_race/usecase/common.py`。`answer_spike` を通して確かめる）。どれも引数と事前状態
（スプリントの状態、実行ロック、スパイクの状態、プランナーの設定）で振る舞いが変わる。

対象外:

- `BackgroundRunner.start_run` / `stop_run` / `ensure_not_running` の実行ロックの因子: CLI から切り出しただけで、
  `start_sprint` / `resume_sprint` / `stop_sprint` の組み合わせ（I・J・K）で実行ロックのすべてのクラスを通す
- `start_run` のプロジェクト名の因子（`/`・`..` を含む名前）: ログとロックのファイル名にプロジェクト名をそのまま使うのは
  CLI から引き継いだ既存の振る舞いで、ST-3 は「CLI の振る舞いを変えない」ため範囲外（別途申告済み）。
  R で `start_refine` の名前の因子を確かめているのは、見直しのログが ST-3 で新しく追加したものだから
- `server.py` での登録: 組み合わせとして分ける値を持たない（説明の文言は `tests/test_mcp_human_tools.py` で確認する）

テストは `tests/test_mcp_human_tools_combinations.py`。モックするのはプロセスの起動（spawn）だけ。
「例外」は DomainError になり、スプリントなどの状態が変わらず、プロセスを起動しないことまでを確かめる。

期待値の出典: タスクの受け入れ条件、README の「人間の判断にあたる操作」の節、ツールの説明、
docs/design.md の R-2（開始条件）・R-4（スパイクの回答を decisions に追加する）・R-6（レビュー完了時の扱い）、
`runner.py` の docstring（別のプロジェクトは並行に実行できる）、CLI と同じ条件（見直しの条件、承認のルール）。

### 境界値表

- on ポイント: 追加前の件数が N − 1。追加できて N 件になる

型の端として N = 1（最小の意味のある上限）と、既定値 N = 5 を使う。

| 対象 | 比較・制限 | 仕様の出典 |
| --- | --- | --- |
| `HumanTools.reject_plan` | コメントの空白を除いた長さが 0 かどうか（`comment.strip()`） | 受け入れ条件「差し戻しはコメントを必須とする」、README「コメントは必須（空は不可）」 |
| `story_to_refine`（`answer_spike` を通す） | ストーリーの未解決のスパイクの件数が 0 かどうか | 受け入れ条件「未解決のスパイクがなくなった場合は…見直しが始まる」（CLI と同じ条件） |
| `HumanTools.answer_spike` の返り値 `decision` / `remaining_spikes` | 決定事項のリストの末尾（`decisions[-1]`）、残りのスパイクの件数 | docs/design.md の R-4（回答を decisions に追加する）、返り値の項目の説明（追加した内容・残っている未解決のスパイク） |

起点は「## 組み合わせテスト」節の ST-3 の同値クラス。M（comment: 空 / 空白だけ / ASCII / 非 ASCII）の「空白だけ」と
「文字あり」の境目、L（回答後の残りのスパイク: なし / 残る）の境目、R（プロジェクト名）の長さの端を境界にした。

対象外: `BackgroundRunner.start_run` のスプリントの実行ログのファイル名（`f"{project_name}-{stamp}.log"`）。
プロジェクト名をそのまま使うため、名前が 235 バイト前後を超えると作成できなくなる（ENAMETOOLONG）。ただし CLI の `_run` から
移しただけの以前からの処理で、ST-3 は「CLI の振る舞いを変えない」ため範囲外とし、別途申告した（組み合わせテストの節の対象外と同じ扱い）。
`list_spikes` の「ストーリーが 0 件なら空」（`if not stories`）は、組み合わせテストの N2（0 件）・N3／N5（1 件以上）で
両側を確かめているため、ここでは重ねない。`resume_sprint` の `sprint.status != ACTIVE` は状態の比較で、境界値ではない
（組み合わせテストの J で扱う）。

補足（ログのファイル名の長さの境界の置き方）:

- 仕様から導ける境界は、ファイル名全体の上限 255 バイトだけ。プロジェクト名の側でどの長さが上限をまたぐか（入力の側の
  境界の位置）は、接尾辞の長さや符号化の方法（実装の詳細）で決まり、仕様からは導けない。実装の切り詰めの位置
  （`file_stem` の 200 バイト）も実装の値で、仕様ではない
- そこで、境界の位置を実装から逆算して on / off の 2 点を置く代わりに、そのままでは 255 バイトを十分に超える長さまで、
  1 文字刻みですべての長さを試す（HB17〜HB19）。上限をまたぐ前後の長さは必ずこの範囲に含まれる
- このため、切り詰めの位置を 1 ずらしても（例: 200 を 201 にする）、ファイル名が 255 バイト以下に収まる限りテストは落ちない。
  それは仕様違反ではないため、落ちないのが正しい。落ちるのは、ファイル名が 255 バイトを超える変更（切り詰めをなくす、
  切り詰めの位置を 236 バイト以上にする）と、切り詰めで別の名前が同じファイル名になる変更（ハッシュを付けない）
- HB5〜HB7 は、前後に空白がない入力（HB5・HB6）はコメントがそのままの形で残ることを、前後に空白がある入力（HB7）は
  空白以外の文字が残ることだけを確かめる。前後の空白を保存時に取り除くかどうかは仕様不明

#### 仕様不明（テストを書かない）

| 境界 | 理由 |
| --- | --- |
| ゼロ幅空白（`\u200b`）だけのコメント | Python の `str.strip()` は空白とみなさないため、受け付けられる。見た目は空なので拒否すべきかもしれないが、仕様に定めがない |
| 差し戻しコメントの前後の空白を保存時に取り除くか | 仕様に定めがない（実装はそのまま保存する） |
| コメント・回答・フィードバックの本文の長さの上限 | 仕様に長さの制限がない |
| ストーリー ID が長い場合の見直しのログのファイル名 | ストーリー ID は `ST-<連番>` として自動で振られ、長い ID は現実には現れない。ID の長さの上限が仕様にない。参考までに、今の実装での境界の位置: プロジェクト名の部分が最大の 200 バイトのとき、ファイル名は「200 + 区切り 1 + ストーリー ID を符号化した部分 + 接尾辞 20」バイトになる。ストーリー ID を符号化した部分が 34 バイト以下（`ST-` に続く数字が 27 桁以下。`S`・`T` は大文字なので 1 文字 3 バイトに符号化される）なら作成でき、35 バイトから作成できなくなる。ID の長さを制限するか、ファイル名全体を 255 バイトに収めるかは人間の判断が必要 |
| 見直しのログのファイル名の時刻の精度 | 同じストーリーの見直しを 1 秒以内に 2 回起動すると、同じファイルに追記される。ログを起動ごとに分けるべきかが仕様にない（計画ジョブのログと同じ扱い） |
| 停止の対象の pid の下限（`stop` の `pid <= 0`） | `runner.stop` は今回の変更ではない既存の処理。pid が読めない（0）場合は組み合わせテストの K6 で確かめている |

## 例外テスト

### 対象

起点にしたのは、次の 3 つ。
- 「## 組み合わせテスト」節で「例外」とした行
- 今回追加したコードの `raise` / `except`
- 今回追加したコードの外部呼び出し（ロックファイル・状態ファイル・サブプロセスの起動）

| 対象 | 例外の発生・受け止め |
| --- | --- |
| `PlanningTools` の各ツール | 既存のユースケースのルール違反（DomainError とそのサブクラス）を、そのまま呼び出し元へ伝える。計画の作成中は `_ensure_not_planning` で DomainError を投げる |
| `PlanningTools.plan_sprint` | プランナー未設定、計画を変更できないスプリントの状態、ジョブの二重起動で DomainError を投げる |
| `call_tool`（`mcp/planning_tools.py`） | MCP のツールとして呼ぶときの変換。利用者に見せるエラー（DomainError・WorkspaceError・PlannerError。CLI と同じ型）を ToolFailure に変え、それ以外の例外はそのまま伝える。`server.py` は ToolFailure をエラーの結果（isError）に置き換えるだけ |
| `PlanJobs.start` | ロックが取れなければ DomainError。起動器（サブプロセスの起動）の例外は、どの型でも失敗の状態を書いてから伝える。OSError だけは DomainError に包む |

利用者に見せるエラーの型を CLI（`cli/main.py`）とそろえるために含めており、そのことをコードのコメントに明記した。

メッセージの要点は、CLI の「エラー: ...」と同じ既存のメッセージから、理由を表す語句を選んで確かめる。受け入れ条件の「ルール違反はエラーメッセージとして返る」に対応する。

### ST-3: 人間の判断にあたる操作（XH1〜XH35）

#### 対象

起点にしたのは、次の 4 つ。
- 「## 組み合わせテスト」節の ST-3（I〜Q）で「例外」とした行（そこでは型を DomainError までしか見ていない）
- ST-3 で追加したコードの `raise` / `except`
- ST-3 で追加したコードの外部呼び出し（サブプロセスの起動・ログのディレクトリの作成・ロックファイル・git）
- 切り出した処理の例外が CLI に以前と同じ形で伝わること（「CLI の振る舞いを変えない」）

| 対象 | 例外の発生・受け止め |
| --- | --- |
| `HumanTools._launch`（start_sprint・resume_sprint・answer_spike の見直しから使う） | プロセスの起動の OSError（ログのディレクトリを作れない・実行ファイルがないなど）を DomainError「プロセスを起動できませんでした: <理由>」に包む（`from e` で元の例外を残す）。OSError 以外の例外は包まずに伝える |

| `HumanTools.resume_sprint` | active でなければ DomainError「スプリント #n は実行中ではありません」（仕様不明。下記） |
| `BackgroundRunner.ensure_not_running` / `start_run` | 実行中なら DomainError「このプロジェクトのスプリントは既に実行中です（pid N）」 |
| `BackgroundRunner.stop_run` | 実行中でなければ DomainError「<project> のスプリントは実行されていません」。pid が読めなければ既存の `stop` が DomainError「実行中のプロセスを特定できません」 |
| 既存のユースケース（SprintService.start・PlanningService・ReviewService） | ルール違反の DomainError（サブクラスを含む）と、git の失敗の WorkspaceError をそのまま伝える |
| `server.py` の `as_tool`（ST-2 の共通処理） | DomainError・WorkspaceError・PlannerError を、日本語のメッセージだけの isError の結果に変える。それ以外の例外は SDK が汎用のエラーの結果にする |
| CLI（`sprint stop`・`sprint resume --detach`） | 切り出した `BackgroundRunner` の DomainError を、以前と同じメッセージで伝える（`main()` が「エラー: ...」と表示する） |

メッセージの要点は、受け入れ条件の「理由を説明するエラー」に対応する語句（既に実行中・実行されていません・コメントが必要・
承認されていません など）で確かめる。CLI の XH31・XH32 は、切り出し前の `cli/main.py` と同じ文言であることを完全一致で確かめる。

外部の失敗の起こし方:
- git の失敗: 存在しないベースブランチを設定したプロジェクトで開始する（本物の git）
- プロセスの起動の失敗: 本物の `spawn_detached` を使い、ログのディレクトリの場所にファイルを置いて作れなくする（ファイル境界）
- 実行中のプロセス: 実行ロックを持つ（組み合わせテストの `lock_state`）
- 想定外の例外: プロセスの起動を、RuntimeError を投げる偽物に差し替える（XH28・XH30 のみ）

## 状態遷移テスト

### 対象

今回追加した**計画ジョブ**（`PlanJobs`・`run_plan_job`・`PlanningTools.plan_sprint` / `get_plan_status`、およびジョブの状態で振る舞いが変わる計画変更のツール）。
プロジェクトごとに 1 つの状態を持ち、呼び出しの履歴（始めたか・終わったか・異常終了したか）で振る舞いが変わる。

スプリントとストーリーの状態（planning → approved → active → review → closed、backlog ⇔ planned）は既存のドメインの状態機械で、今回は変更していない。
MCP のツールから見た各状態での振る舞いは、「## 組み合わせテスト」節の B〜F（スプリントの状態 S × 計画ジョブ J）で網羅している。
この節では、スプリントの状態は e8（計画を変更できないスプリントの状態での開始）としてだけ扱う。

期待値の出典:
- README の MCP の節（plan_sprint はすぐに返り、get_plan_status で確認する。作成中は計画を変更するツールがエラーになる）
- 受け入れ条件（時間がかかってもタイムアウトしない、ルール違反はエラーメッセージとして返る）
- docs/spec.md の R-3（承認後は計画を変更できない）

D（異常終了）と C（状態ファイルの破損）の扱いの主な根拠は、今回の実装で書いた `plan_job.py` の docstring と、例外テストの節での判断（X18・X26）。
妥当と考えるが、**人間の確認が要る**。

### 状態の一覧

| 状態 | 意味 | get_plan_status の見え方 |
| --- | --- | --- |
| N（初期状態） | 一度も計画を始めていない | `not_started` |
| R | 計画の作成中（プロセスがロックを持っている） | `running` |
| S（終了状態） | 計画を作って結果を書いた | `succeeded`（スプリント番号・ゴール・ストーリーを含む） |
| F（終了状態） | 失敗して理由を書いた（プランナーの失敗・起動の失敗など） | `failed`（error に理由） |
| D（終了状態） | 結果を書かずにプロセスが終わった。状態ファイルは running のまま残り、問い合わせのときに判定される | `failed`（error に「異常終了」） |
| C（終了状態） | プロセスがなく、状態ファイルが壊れていて読めない | 仕様不明（今は ValidationError がそのまま伝わる） |

S・F・D・C は終了状態だが、計画をやり直す（e1）ことで R に戻れる。

### イベントの一覧

| イベント | 内容 |
| --- | --- |
| e1 開始 | `plan_sprint`（計画を変更できるスプリントの状態で呼ぶ） |
| e2 成功の結果 | 作成中のジョブのプロセスが計画を作り、結果を書いて終わる |
| e3 失敗の結果 | 作成中のジョブのプロセスがプランナーの失敗で結果を書いて終わる |

| Q4 | N →e5→ F →e5→ F →e1→ R →e2→ S | 起動の失敗が続いても、ロックが残らないこと |
| Q5 | N →e1→ R →e7（拒否）→ R →e2→ S →e7（成功） | 作成中は計画の変更が拒否され、終わった後は同じ変更ができること |
| Q6 | N →e1→ R →（人間が承認）→ e2 → F →e8（拒否）→ F | 作成中に承認されると、ジョブは「終了していません」で失敗し、承認済みの計画は置き換えられないこと。その後の開始も拒否されること |
| Q7 | N → e1 と e1 が同時 → R | 2 つの開始が同時に来ても、始まるジョブとプロセスは 1 つだけであること（10 回繰り返す） |

### 仕様不明

| 対象 | 理由 |
| --- | --- |
| `caucus plan run` の直接実行（全状態） | 内部用の隠しコマンドで、人間が直接実行したときの振る舞いは受け入れ条件にも README にもない。R で直接実行すると、ジョブのプロセスと並行して計画の処理が走る |
| C での問い合わせ（e6） | 状態ファイルが壊れているときに failed として返すのか、エラーにするのかが仕様にない（別途報告済み） |
| R での e8（承認後の開始） | 「承認後」と「作成中」の 2 つの理由が重なったときに、どちらで拒否するかが仕様にない |
| キャンセル | 計画の作成を途中で止めるイベントは、今回のツールにない（`caucus sprint stop` はスプリントの実行用）。止めたい場合の扱いは仕様にない |

### 補足: `finish` での上書き

実際の流れで `finish` が上書きするのは、R の状態ファイル（running）だけ。開始（e1）のたびに状態ファイルを running で書き直すため、S の結果を `finish` が直接上書きする場面はない。
そのため、「`finish` が既存の成功の結果を上書きしない」ように壊しても、このテスト群では落ちない（直接実行は仕様不明のため扱わない）。
前の結果が置き換わることは、Q1（成功 → やり直し → 失敗 → 再試行 → 成功で、ゴールと理由が毎回この回のものになる）と、各セルの e1（前の結果を引きずらない）で確かめる。

### ST-3: スプリントの状態 × 実行プロセス（人間の判断にあたる操作のツールから見た状態遷移）

#### 対象

ST-3 で追加した `HumanTools` のうち、スプリントの状態と実行プロセスの有無を変える（またはそれに依存する）ツール:
approve_plan・reject_plan・start_sprint・stop_sprint・resume_sprint・get_review・add_feedback・complete_review。
状態は「スプリントの状態（DB）」と「実行プロセスがいるか（起動した直後か、実行ロックを持っているか）」の組で、
同じ呼び出しでも、それまでの呼び出しの履歴（承認したか・開始したか・止めたか・レビューを完了したか）で結果が変わる。

スプリントの状態機械そのものは既存（ST-3 では変えていない）だが、ST-3 で実行プロセスの起動・停止が MCP から
操作できるようになり、active が「起動直後」「実行中」「停止中」に分かれて見えるようになったため、この組を状態とした。

対象外（別の節・別のテストで網羅している、または表の前提として固定したもの）:
- スパイクの状態（open → answered / dropped）と answer_spike: 組み合わせテスト L1〜L21、境界値テスト HB8〜HB13
- list_spikes: 状態を変えない参照のツール
- 計画ジョブの状態: この節の ST-2 の部分
- 実行ロックの細かい違い（pid を読めないロック・前回の実行が残した空のロックファイル・別のプロジェクトのロック・
  active 以外の状態でのロック）: 組み合わせテスト I1〜I30（開始）・J1〜J16（再開）・K1〜K7（停止）と、
  例外テスト XH10〜XH13 で網羅している。この表では、空のロックファイルと別のプロジェクトのロックは「実行プロセスなし」、
  pid を読めないロックは「実行中」と同じに扱われることを、それらのテストで確かめている
- PLANNING は「ストーリーが 1 件以上ある」計画中とする（表の PLANNING-approve → APPROVED はこの前提）。
  ストーリーが 0 件の計画中の承認は、組み合わせテスト M3・例外テスト XH17 で例外になることを確かめている

テストは `tests/test_mcp_human_tools_state_machine.py`。

期待値の出典: 受け入れ条件（開始と再開はバックグラウンドで実行し pid とログを返す。実行中の開始・再開と、実行中でないときの
停止はエラー（二重に起動しない）。停止は実行中のプロセスに停止を指示する。差し戻しはコメント必須）、README の
「人間の判断にあたる操作」の節（各ツールは `caucus sprint approve` などの CLI 相当）、docs/design.md の R-2（開始できるのは
approved のみ）・R-3（承認後は計画を変更できない）・R-6（レビュー完了でスプリントを closed にする）、
既存の CLI と同じ規則（差し戻しは planning / approved から。フィードバックとレビュー完了は review でのみ。
`caucus review show` は review のスプリントでのみ資料を表示する — get_review は README で `caucus review show` 相当としている）。

#### 状態の一覧

| 状態 | 意味 | スプリント（DB） | 実行プロセス |

| NONE（初期状態） | 終了していないスプリントがない（一度も作っていない） | なし | なし |
| PLANNING | 計画中（ストーリーが 1 件以上） | planning | なし |
| APPROVED | 承認済み・開始前 | approved | なし |

テストでの代用:
- LAUNCHING の実行プロセス: ロックを取らずに眠るだけの本物のプロセス（新しいプロセスグループで起動する。本物の起動と同じ）
- RUNNING の実行プロセス: 実行ロックを持って眠るだけの本物の子プロセス（stop_sprint で実際に止められる）

  終了済みのプロセスのもので、「起動したプロセスがすぐにロックを取って終わった」扱いになる。このため「RUNNING への遷移」は
  「スプリントが active になり、実行プロセスを 1 回起動したこと」で確かめる
- STOPPED は、開始した直後の状態（全ストーリーが queued）で作る。実行の途中で止めた（running のストーリーが残る）STOPPED からの
  再開は、別のテストで確かめる

#### この観点で見つかった実装の誤り

- **起動の直後（実行プロセスがまだ実行ロックを取っていない間）に、開始・再開を二重に受け付けていた。**
  `BackgroundRunner.start_run` は実行ロックだけを確認してから起動し、ロックは起動された子プロセスが取る。このため、開始・再開の
  直後にもう一度再開（または開始・再開）を呼ぶと確認を通り、実行プロセスを 2 つ起動して、どちらも成功（pid）を返していた
  （2 つ目のプロセスは自分の中でロックが取れずに終わる）。受け入れ条件「既に実行中のスプリントを開始・再開しようとしたときは、
  二重に起動せず、理由を説明するエラーを返す」に反する。同じ間の stop_sprint も「実行されていません」になっていた。
  - 修正: `start_run` が起動したプロセスの pid を印のファイル（`run_dir/<project>.launched`）に残し、ロックがなくてもその pid が
    生きていれば実行中とみなす（`ensure_not_running`）。`stop_run` も、その pid（プロセスグループの先頭）に停止を送る。
    プロセスが終われば（ロックを取れずに終わった場合も）印は無視される
  - CLI の `caucus sprint start --detach` / `resume --detach` も同じ処理を使うため、直後の二重起動を拒否するようになる
    （それ以外の CLI の出力と振る舞いは変わらない）
  - テスト: 表の LAUNCHING の行、SQ7〜SQ11。修正前の実装では 7 件が落ちることを確かめた

#### 仕様不明（テストを書かない）

| 対象 | 理由 |
| --- | --- |
| 停止中でないスプリントの resume（表の 5 セル） | 上記のとおり |
| APPROVED → start で、開始を確定した後に実行プロセスの起動に失敗したときの遷移先 | active とブランチが残り、実行プロセスはない（見かけ上 STOPPED）。STOPPED に遷移するのが仕様なのか、APPROVED に戻すべきかが仕様にない（例外テストの節の XH7 と同じ）。今の実装では resume で起動し直せ、start は R-2 で拒否されるが、どちらが正しい復旧の手順かは人間の判断が必要 |
| REVIEW で、実行プロセスがまだ終わっていない（ロックを持っている）とき | 実行プロセスは review に進めてから通知して終わるため、その短い間は「REVIEW かつ実行ロックあり」になる。この間の add_feedback・complete_review はロックを見ずに受け付けられる。実行プロセスはもう DB を変えないので問題は起きないと考えるが、仕様に定めがない |
| RUNNING で実行プロセスが異常終了したとき | active のまま実行プロセスがなくなり、STOPPED と同じに見える。resume で再開できる（STOPPED の行と同じ）が、異常終了を知らせるかどうかは ST-3 の範囲外（既存の通知） |
| stop の直後、実行プロセスが SIGTERM を受けて終わるまでの間 | RUNNING と STOPPED の間の一時的な状態。stop_sprint は停止を指示して返るため、その間に resume を呼ぶと「既に実行中」になる。この間の扱い（待つか、例外にするか）が仕様にない |
| 同時の呼び出し（MCP と CLI から同時に、または 2 つの MCP サーバーから同時に開始・再開する） | 1 つの MCP サーバーの中ではツールは 1 つずつ実行される（ST-2 の `as_tool`）。別のプロセスから同時に呼ぶと、「確認してから起動して印を書く」までの間（ミリ秒単位）が重なれば二重に起動しうる。起動側でロックを取って子プロセスに引き継ぐ（計画ジョブと同じ）方式にすれば閉じられるが、CLI の `sprint run` の作りを変えるため範囲外とした（別途申告） |

## プロパティテスト

### 前提: Hypothesis が未導入（テストは生成した入力でまだ一度も動いていない。この観点は「未実施」）

`uv add --dev hypothesis` は、この作業環境の権限で拒否された。回避はしていない。
テストは `tests/test_mcp_planning_properties.py` に Hypothesis で書いた。冒頭の `pytest.importorskip` により、Hypothesis が入るまでは**理由付きで skip** される（`pytest -rs` で理由が表示される）。
**この観点の目的（人が思いつかなかった入力で誤りを見つけること）は、まだ果たせていない。**
**人間の判断が要る:** Hypothesis を開発用の依存に追加するかどうか。

性質を確かめる本体は通常の関数（`check_*`）にした。Hypothesis の `@given` はそれに入力を渡すだけにしている。
今回は、手で選んだ入力（各テストの `@example` と同じもの）で `check_*` を直接呼び、全件が通ることを確かめた。あわせて、実装を壊すと対応する `check_*` が落ちることも確かめた。
生成した入力で動かすと、まだ見つけていない入力で落ちる可能性がある。

### 入力の文字列の方針（サロゲートの扱い）

| 対象 | サロゲートを生成するか | 理由 |
| --- | --- | --- |
| P1・P2（`file_stem`） | する | 任意の `str` を受け付ける純粋な関数で、契約上は型が受け付けるすべての文字列が対象。JSON の `"\ud800"` から入りうる |
| P3〜P8（DB・状態ファイルを通る処理） | しない | 既存の永続化（pydantic の JSON・SQLite）がサロゲートを保存できず、プロジェクトの登録もストーリーの起票も失敗する。そのため、サロゲートを含むプロジェクトやストーリーは作れない（確認済み）。入口（MCP のツール）でルール違反として分かりやすく拒否するかどうかは仕様不明で、別途報告する |

通常の文字列（`st.text()`）に加えて、非 ASCII だけの長さ 0〜100 文字の文字列を混ぜて生成する。エンコードで長くなり、`file_stem` の切り詰めの分岐を通すためである。
`file_stem` 用には、通常の文字とサロゲートが混ざった文字列も生成する。

### この観点で見つかった実装の誤り

`file_stem` の性質（P1）を、手で選んだ入力で確かめたところ、次の 2 つが見つかった。どちらも `file_stem` の中で直した。

- **長いプロジェクト名でファイル名の上限（255 バイト）を超える。** 日本語は URL エンコードで 9 倍の長さになり、28 文字程度で上限を超える。`plan_sprint` が生の `OSError: File name too long` になっていた。
  - 修正: 名前の部分が 200 バイトを超える場合は先頭を残し、名前全体の SHA-256 を付ける。区切りの "%%" はエンコードの結果には現れないため、短い名前の結果とは重ならない。
- **サロゲート（`\ud800` など）を含む名前で `quote` が UnicodeEncodeError になる。**
  - 修正: `surrogatepass` でエンコードする。

**この修正の範囲:** 直したのは `file_stem`（ファイル名の作り方）だけである。サロゲートを含む値は、計画ジョブの状態ファイル（JSON）にも、DB（プロジェクトの登録・ストーリーの起票）にも保存できず、どちらも利用者向けでないエラーになる。
既存の永続化の制約で、サロゲートを含むプロジェクトは登録できない。そのため、計画ジョブにサロゲートを含む名前が渡ることは、ツールを通しては起きない。入口でどう拒否するかは仕様不明として、別途報告した。
